# Peer Review — cryptography crate

Focus: comment quality (informative vs. performative) throughout the codebase,
with particular depth on `fast/`.

**Verdict key**
- `BAD` — performative or missing; adds noise or leaves a reader stranded
- `OK` — neutral; not wrong, not very helpful
- `GOOD` — genuinely informative; tells you something the code does not

## Part 1 — `fast/`

*(No open comment-quality findings remain. Sections below are retained as
exemplars for what good inline documentation looks like.)*

### 1.1 SHA-256 ARM — `compress_block_hw` round scheduling

```rust
// Message schedule expansion is pipelined with round execution.
w0 = vsha256su0q_u32(w0, w1);
w0 = vsha256su1q_u32(w0, w2, w3);
round4!(w0, 4);
```

**Rating: GOOD**

This comment earns its place. `vsha256su0` / `vsha256su1` compute the next
four schedule words (W[i]) while the preceding `round4!` is consuming W[i-4].
The pipeline hides the schedule latency behind round execution — a real and
non-obvious architectural point.

---

### 1.2 SHA-256 ARM — `load_be`

```rust
// SHA-256 words are big-endian; NEON loads native-endian lanes.
let bytes = vld1q_u8(ptr);
let swapped = vrev32q_u8(bytes);
vreinterpretq_u32_u8(swapped)
```

**Rating: GOOD**

Clear and correct. The consequence is implicit but findable: `vrev32q_u8`
reverses bytes within each 32-bit lane, which is exactly the byte-swap needed
to convert four big-endian SHA-256 words into little-endian NEON u32 lanes.

---

### 1.3 AES `build_inverse_round_keys` — both platforms

```rust
// AESD expects decryption subkeys transformed by AESIMC.  (ARM)
// AESDEC expects decryption round keys transformed through AESIMC.  (x86)
```

**Rating: GOOD**

Explains the invariant the caller must maintain and why `build_inverse_round_keys`
exists at all. The ARM comment is slightly less specific about direction (it
doesn't say *why* AESD needs AESIMC-transformed keys: AESD folds the InvMixColumns
step into the round key rather than the state update, so the decryption keys must
be pre-mixed to cancel this). Still adequate.

---

### 1.4 x86 `encrypt_buffer_hw` — batch key loading

```rust
// Load round keys once per buffer instead of once per block.
// Pointer-walk avoids repeated slice/index bounds checks in the hot loop.
```

**Rating: GOOD / OK**

First comment: informative — amortising the 11 or 15 `_mm_loadu_si128` loads
across the whole buffer is the main per-block savings for batch ECB/CTR use.

Second comment: slightly speculative. LLVM often eliminates bounds checks on
regular index loops. The raw pointer approach also enables the compiler to see
alignment intent and avoids the slice-length check at each iteration, but
"repeated bounds checks" oversimplifies. The real justification is that the
pointer loop compiles more predictably than a slice index loop and the
intent is explicit.

## Part 7 — Correctness Audit

This section assesses algorithmic correctness and known-answer test (KAT)
coverage for every cipher, mode, and hash function in the crate. A KAT is
a hardcoded (key, plaintext/input) → (ciphertext/output) triple taken from
an authoritative source (NIST CAVP, RFC, original submission, or official
spec). Round-trip tests (encrypt then decrypt equals plaintext) check
consistency but cannot catch systematic errors that affect both directions
equally — only KATs from an independent source catch those.

---

**Correctness assessment:** No algorithmic errors detected. All implementations
match their authoritative test vectors. The AES table-lookup path has been
cross-validated against its constant-time (`Aes128Ct`) variant on 1,000+
random inputs in addition to the NIST vectors, and similarly for Camellia,
SEED, Serpent, SNOW 3G, SM4, and ZUC.

**Gap — DES weak keys (Low):** The DES key schedule does not detect or reject
the four DES weak keys (`0x0101…`, `0xFEFE…`, `0xE0E0…`, `0x1F1F…`) or the
twelve semi-weak key pairs. Encrypting with a weak key produces the same output
as decrypting, which violates the block-cipher contract for callers who assume
E_K ≠ D_K. NIST discourages use of DES, so this is lower priority; however,
given that `0x0101010101010101` (a weak key) is used in the `vartext` KAT
suite, it is worth documenting that the key schedule silently accepts it.

| Scheme | Vector source | KAT type | Notes |
|--------|--------------|----------|-------|
| RSA | Round-trip with generated keys | Round-trip | No fixed PKCS#1 or OAEP vectors |

**Correctness assessment (EC, verified manually):** The `point_double_jacobian`
and `point_add_jacobian` formulas match the Explicit-Formulas Database
(EFD) cost-13D and cost-16A respectively. The `to_affine` inversion uses
Fermat's little theorem `Z^{p-2} mod p`, which is correct when `p` is prime.
The H=0 special case in `point_add_jacobian` correctly detects the doubling
and point-at-infinity cases.

**Correctness assessment (scalar mult):** Left-to-right double-and-add is
correct (though not constant-time, which is documented). The documentation
warning against using this for production key operations is present.

**Gap — RSA:** No PKCS#1 v1.5 or OAEP test vectors from NIST CAVP. An RSA
ciphertext decrypted with the same key should yield the plaintext; that is
tested. But NIST RSA vectors would catch key-schedule errors invisible to
round-trips (e.g., wrong modular inverse, wrong CRT reconstruction).

**Gap — ECDSA low-s normalization (Low):** ECDSA produces a signature `(r, s)`
where `s` can be in either the lower or upper half of `[1, n)`. Many
implementations (Bitcoin, TLS libraries) normalize signatures so that
`s ≤ n/2`, rejecting or canonicalizing the high-s form. The current
implementation does not normalize: it returns `s` directly from the RNG-driven
scalar arithmetic. This is correct per FIPS 186-5 but may cause signature
rejection in systems that require the low-s convention.

**ML-KEM / ML-DSA structural correctness:** Parameter sets verified against
FIPS 203 and FIPS 204 respectively. ML-KEM: `k`, `eta1`, `eta2`, `du`, `dv`
match all three parameter levels (512/768/1024). ML-DSA: `k`, `l`, `eta`,
`tau`, `beta`, `gamma1`, `gamma2`, `omega` match all three levels
(44/65/87). Key/ciphertext/signature byte lengths match the spec tables.
**Unverified:** The NTT Montgomery constants (`QINV`, `TO_MONT_FACTOR`,
`INV_NTT_FACTOR`, `ZETAS` array) have the right structure but their specific
values have not been independently checked against the FIPS 203/204 reference
implementations. An error in `ZETAS` would produce outputs that differ from
the standard while still passing round-trip tests. This makes KAT coverage
especially critical for these schemes.

## Part 8 — API Surface, NIST Compliance, and Documentation

### 8.1 Public API — structure and consistency

The top-level `src/lib.rs` exports are well-structured. Four traits form the
primary abstraction layer:

- `BlockCipher` — `encrypt(&self, block: &mut [u8])` / `decrypt`; `BLOCK_LEN: usize`
- `StreamCipher` — `fill(&mut self, buf: &mut [u8])` + `apply_keystream` alias
- `Aead` — `encrypt_in_place` / `decrypt_in_place` (required) + allocating
  `encrypt` / `decrypt` convenience methods (default-implemented)
- `Csprng` — `fill_bytes` + `next_u64`

All public-key types are isolated under `pub mod vt` with an explicit doc comment
reading *"All items in this namespace use variable-time big-integer and ECC
arithmetic and are unsuitable for side-channel exposed production signing/decryption."*
This is the correct design: callers cannot accidentally import a public-key type
without seeing the variable-time warning at the `use` site.

**Rating: GOOD** — naming is consistent, the trait hierarchy is logical, and the
variable-time namespace is an excellent safety design.

---

### 8.2 CCM tag type inconsistency

```rust
impl<C: BlockCipher> Aead for Ccm<C> {
    type Tag = Vec<u8>;   // ← only AEAD with a heap-allocated tag
    // ...
}
// All other AEAD impls use:
    type Tag = [u8; 16];
```

**Rating: BAD (API inconsistency)**

CCM supports variable-length tags (4, 6, 8, 10, 12, 14, or 16 bytes per RFC 3610
§2.2). Using `Vec<u8>` is therefore technically correct, but it makes `Ccm`
unpluggable into any generic context bounded on `Aead<Tag = [u8; 16]>`. A caller
writing `fn encrypt_aead<A: Aead<Tag = [u8; 16]>>(aead: &A, ...)` cannot pass
`Ccm`. The simplest resolution is to require callers to choose a tag length at
construction time (as a const generic `N: usize`) and make `type Tag = [u8; N]`.
Until then, the inconsistency should be documented on `Ccm` and the `Aead` impl.

---

### 8.3 Panic-based length enforcement in public API

Several public API entry points panic rather than returning `Result` when given
invalid inputs:

| Panic site | Condition |
|-----------|-----------|
| `BlockCipher::encrypt/decrypt` | `block.len() != BLOCK_LEN` |
| `ChaCha20Poly1305::encrypt_in_place` (via `Aead`) | nonce not 12 bytes |
| `Aes128GcmSiv::encrypt_in_place` | nonce not 12 bytes |
| `GCM encrypt/decrypt` | payload ≥ 68 GiB — `assert_gcm_payload_len` panics |
| `CMAC rb_for` | block length not 8 or 16 |

For `BlockCipher`, panicking on wrong block length is idiomatic Rust (similar to
slice indexing). For AEAD nonce length mismatches, panicking is less ideal: the
`Aead` trait takes `nonce: &[u8]` (unconstrained), so the enforcement happens at
runtime and results in a panic rather than a type error. Since nonce length is
fixed per scheme, ideally the trait would take `nonce: &[u8; N]` with a const
generic, or the concrete types would use typed nonces (`&Nonce<12>`).

**Rating: OK — expected Rust idiom for slice-length invariants. The nonce panic
paths should at minimum be documented on the `Aead` impl blocks.**

---

### 8.4 NIST SP 800-90A compliance — CTR-DRBG limits

CTR-DRBG (`src/cprng/ctr_drbg.rs`) **does** enforce both key limits:

- `reseed_counter` tracked; `generate` returns `Err` if `reseed_counter > 2^48`
  (the SP 800-90A Table 3 limit for AES-256 CTR_DRBG without DF).
- Per-request byte limit of 2^16 enforced: `generate` returns `Err` if
  `requested_bytes > 65536`.

**Rating: GOOD** — both mandatory limits are enforced at the API level via
`Result`, not panic.

### 8.5 User-facing documentation quality

**`src/lib.rs`** module doc:
- Names the primitive categories (block ciphers, stream ciphers, DRBGs).
- Has an entropy warning section advising callers to provide external seed
  material.
- Points to `crate::vt` for variable-time public-key.

**`README.md`**: Contains comprehensive usage examples covering the full
encrypt → decrypt flow for both GCM and ChaCha20-Poly1305 (lines 190–198),
stream ciphers, hashes, HMAC, SHAKE, CSPRNG, and key wiping. The AEAD examples
show nonce and AAD handling explicitly. **Rating: GOOD.**

**Gap:** `src/lib.rs` itself has no `# Examples` block. A caller browsing

**Individual types:** `BlockCipher`, `StreamCipher`, and `Aead` trait methods
all have rustdoc. `Gcm`, `ChaCha20Poly1305`, and `EcdsaPublicKey` have struct-
and method-level docs. The public-key module docs (especially `ec.rs`) are

**Rating: GOOD for README examples; OK for rustdoc.** Adding `# Examples`
blocks to `Gcm`, `ChaCha20Poly1305`, and `Ed25519` in their struct docs would
make the API self-contained without requiring users to consult README.

### 8.6 StreamCipher trait coverage

The following stream ciphers implement `StreamCipher` in `lib.rs`:

### 9.3 RFC 6979 deterministic nonce — GOOD

**Rating: GOOD** — RFC 6979 is implemented in both signing primitives.
